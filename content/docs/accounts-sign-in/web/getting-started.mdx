Before you call any endpoint, configure an **OAuth/OIDC-style client** for your product in the Intastellar developer console (or equivalent registration UI your team uses).

## 1. Register your application

Create an application record and capture:

- **Client ID** — public identifier for your app (safe to ship in front-end code for public clients).
- **Client secret** — only for **confidential** (server-side) clients; never expose in the browser or mobile app binaries.
- **Redirect URIs** — exact HTTPS URLs where Intastellar may return the user after sign-in. See [Redirect URIs and callbacks](/docs/accounts-sign-in/web/redirect-uris).

Use separate client registrations for production and staging so redirect URIs and secrets stay isolated.

## 2. Choose a flow

| Your app | Recommended approach |
| -------- | -------------------- |
| Single-page app (React, Vue, etc.) | Authorization code with **PKCE**; no client secret in the browser. |
| Server-rendered site (session cookies) | Code flow: browser completes the redirect; your **server** exchanges the code using the client secret. |
| Mobile / native | Same ideas as SPA: PKCE, custom URL scheme or HTTPS redirect. |

Details: [Authorization code flow](/docs/accounts-sign-in/web/authorization-code-flow), [SPAs and JavaScript](/docs/accounts-sign-in/web/spa-and-javascript), [Server-side exchange](/docs/accounts-sign-in/web/backend-exchange).

## 3. Endpoints and metadata

Your console should list (or you obtain from discovery):

- **Authorization endpoint** — user is sent here to sign in and approve scopes.
- **Token endpoint** — your backend (or a secure BFF) exchanges the code for tokens.
- **Issuer / JWKS** — for validating ID tokens when you use OpenID Connect.

Placeholders in examples on this site are written as `AUTHORIZATION_ENDPOINT` and `TOKEN_ENDPOINT`; substitute the values from your environment.

## 4. Plan sessions

Decide how your site remembers the user after sign-in:

- **HTTP-only, Secure cookies** set by your server (recommended for traditional web apps).
- **Backend session** with only an opaque session id in the cookie.
- **Short-lived access token** in memory for SPAs, with refresh via a **backend-for-frontend** when possible.

See [Sessions, cookies, and tokens](/docs/accounts-sign-in/web/sessions-and-cookies).
